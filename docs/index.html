How it's built

Code decides. The model narrates.

The single biggest risk in a support agent is asking a language model to compute eligibility from raw data. So it never does — four layers, each with exactly one job.

Data layer
data_store.py · policy_store.py
Loads the fixed order data and policy doc, read-only. No lookup succeeds without a matching customer_id — this is the actual anti-leakage boundary, not a prompt instruction.
CodeModel
Rules layer
rules.py
Plain Python computes return eligibility, refund routing, and delay status directly from policy's stated thresholds — not an LLM judgment call.
CodeModel
Tool layer
tools.py
Nine functions with JSON schemas — the only interface the model has to the data. customer_id is never a model-settable argument in any schema.
CodeModel
Orchestration layer
agent.py
A bounded ReAct loop (max 6 tool calls per turn) against Groq's function calling. If it somehow loops past that budget, it fails closed into a human escalation.

What it won't do

The model can't leak what it can't reach.

customer_id never appears as an argument in any tool schema. It's injected server-side, only after identify_customer succeeds — there's nothing for a prompt injection to override.

Attempted
Forge customer_id=C-101 inside a tool call, after identifying as C-100.
Result
Session identity (C-100) used instead. Forged value silently overridden, not trusted.
test_model_supplied_customer_id_is_ignored_not_trusted — passing
No invented discounts, coupons, or waivers — only the policy-defined ₹250 delay credit exists.
No bank details collected in chat — cash-on-delivery refunds route to a human over a secure link.
No cross-customer order details, even if the person insists it's theirs.
No policy invented where the document is silent — it says so, and offers a human agent.

Stack & decisions

Built to run free, explained honestly.

FastAPI Groq · openai/gpt-oss-120b Python 3.11 Vanilla JS UI Render (free tier) In-memory sessions
Known limitations
  • No real authentication — email/phone match only
  • Business-day math has no holiday calendar
  • Escalation queue is in-memory, single-process
  • No fallback LLM provider if Groq rate-limits
Deterministic rules over LLM reasoning
Near-zero hallucination risk on eligibility, refunds, and delay status — the cases that matter most to get right.
Keyword search over a vector DB
The policy doc is ~1,500 words and static — embeddings would be over-engineering for this scope.
In-memory sessions over Redis
Right-sized for this assignment; wouldn't survive a restart or multi-instance scaling in production.
Before building this for real

Five questions I'd ask Trendly's ops team.

01
What's the authoritative "current time" source in production, and how should date-dependent logic be recalculated if an order's timestamps are corrected after the fact?
02
What does real identity verification look like today, and what's the minimum viable version the agent should require before discussing order details?
03
Is there a public holiday calendar or region-specific business-day definition that should feed into delay and dispatch calculations?
04
What does the human-agent handoff look like operationally — which ticketing system should the escalation payload match, and what SLA applies?
05
At real volume — 2,000 chats a day — what's the expected peak concurrent load, and is there budget for a paid LLM tier beyond the free-tier limits used here?
